# VidMind-AI 面试整理

> 本文档基于 VidMind-AI 项目内容，系统性梳理面试官可能针对此项目提出的各类问题，涵盖项目背景、技术选型、核心实现、架构设计、性能优化、安全性、团队协作等维度。每个问题标注了考察层次，供面试前准备参考。

---

## 一、项目背景与定位

### Q1: 这个项目的初衷是什么？解决了什么痛点？

**考察层次**：基础 · 项目理解

长视频（如网课、技术演讲、会议录像）包含大量结构化信息，但传统方式只能线性播放观看，无法快速定位关键内容。VidMind-AI 的目标是将长视频转化为**可检索、可追溯、可继续追问的结构化知识**——用户只需要输入分析目标，系统就能自动提取关键帧和语音信息，生成带时间戳证据的结构化分析结论。

**个人回答要点**：
- 强调"长视频"与"短视频"的本质区别——长视频信息密度低、时间跨度大，纯人工观看成本高
- 点明差异化：不是简单的视频摘要，而是**有证据支撑的 Agent 分析**

### Q2: 为什么选择做 Video Agent 而不是传统的视频处理 pipeline？

**考察层次**：中等 · 方案设计

传统 pipeline 是固定流程——语音转写、OCR 识别、关键词提取，各环节独立，缺乏对用户意图的理解和反馈闭环。Agent 模式的优势在于：

1. **目标驱动**：Planner 理解用户意图并拆解任务，而非一刀切地全量处理
2. **证据约束**：Executor 的每一条结论都必须绑定时间戳和来源（ASR/OCR），Critic 会校验证据可靠性
3. **闭环修正**：未通过 Critic 校验时，定向补充检索，形成"分析-校验-修正"闭环

### Q3: 市面上有没有类似的开源项目？你们有什么不同？

**考察层次**：中等 · 竞品分析

类似项目如 Video-LLaMA、LLaVA-NeXT-Video 等多模态大模型方案，通常直接将视频帧输入大模型，优点是通用性强，但缺点是**Token 成本极高**，且对长视频的时序信息处理有限。

VidMind-AI 的差异化在于：
- **先结构化再分析**：通过 ASR + OCR 构建结构化 VideoContext，而非直接喂原始视频帧
- **Agent 编排**：Planner-Executor-Critic 三层架构，每个环节可观测、可追溯
- **断点恢复**：支持超长视频的 Checkpoint 持久化，避免中途失败从头重来

## 二、技术选型

### Q4: 后端为什么选择 Spring Boot 3 + Java 21？对比其他框架的考量是什么？

**考察层次**：基础 · 技术选型

Spring Boot 3 是当前 Spring 生态主线版本，Java 21 提供了虚拟线程（Virtual Threads）、模式匹配、Record 等特性。选择理由：

1. **生态成熟**：MyBatis-Plus、RocketMQ、Redisson 等中间件与 Spring Boot 集成度高
2. **虚拟线程**：ASR 和 OCR 的 IO 密集型任务可受益于虚拟线程，降低线程池管理复杂度
3. **Record 类型**：项目中大量使用 `record` 定义 DTO（如 `VideoContext`、`AgentState`、`AnalysisResult`），代码简洁且不可变安全
4. **Undertow**：选择 Undertow 替代 Tomcat，因本项目中 SSE 长连接较多，Undertow 在非阻塞场景下的性能表现更好

### Q5: 为什么用 RocketMQ 而不是 Kafka 或 RabbitMQ？

**考察层次**：中等 · 技术选型

| 维度 | RocketMQ | Kafka | RabbitMQ |
|:---|:---|:---|:---|
| 消息可靠性 | 支持事务消息、重试队列 | 高吞吐、日志型 | 功能全面 |
| 延迟队列 | 原生支持 | 需自实现 | 插件支持 |
| 死信队列 | 原生支持 | 需自实现 | 原生支持 |
| 运维成本 | 中等 | 较高（依赖 ZK） | 较低 |

选择 RocketMQ 的核心原因：
- **死信队列 + 重试机制原生支持**：项目中需要将失败消息投递到独立死信主题，并由管理接口重新投递，RocketMQ 的消费重试和死信队列机制完美匹配
- **消费幂等友好**：RocketMQ 的 Message ID 结合 Redisson 分布式锁，便于实现 Exactly-Once 语义
- **团队熟悉度**：相比 Kafka 的日志型架构，RocketMQ 的队列模型在本项目的任务调度场景中更直观

### Q6: LangChain4j 在项目中扮演了什么角色？为什么选择它而不是 LangChain Python？

**考察层次**：中等 · 技术选型

项目中 LangChain4j 主要用于封装 DeepSeek 模型的 API 调用，提供统一的 `ChatModel` 接口。

选择理由：
1. **Java 生态一致性**：整个后端是 Spring Boot + Java，引入 LangChain4j 避免了跨语言调用（Python 服务）的运维成本和网络延迟
2. **轻量级**：项目只需要基础的 Chat 调用和结构化输出解析，LangChain4j 的 `OpenAiChatModel` 足够满足需求，不需要 LangChain Python 的完整 Agent 框架
3. **结构化输出**：项目中通过 LangChain4j 调用 DeepSeek，再配合 Jackson 手动解析 JSON 结构化输出。之所以没有用 LangChain4j 的 OutputParser，是因为需要更精细的字段校验和降级处理

### Q7: Qdrant 的选型考量是什么？对比 Milvus 和 Pinecone？

**考察层次**：中等 · 技术选型

| 维度 | Qdrant | Milvus | Pinecone |
|:---|:---|:---|:---|
| 部署方式 | Docker Compose 本地部署 | 分布式架构较重 | 仅 SaaS |
| 性能 | 单机性能优秀 | 分布式强项 | 托管服务 |
| 过滤 | 支持 Payload 过滤 | 支持 Scalar 过滤 | 支持 Metadata 过滤 |
| 社区 | Rust 实现，社区活跃 | 较成熟 | 商业化 |

选择 Qdrant 的核心原因：
- **本地部署**：项目需要完全本地可运行，Pinecone 是纯 SaaS 方案不符合要求
- **轻量级**：Milvus 的分布式架构对于本项目的数据量来说过于沉重，Qdrant 单机即可满足
- **Rust 实现**：性能好，资源占用低，适合 Docker Compose 本地编排
- **优雅降级**：项目中设计了 Qdrant 不可用时的本地关键词降级机制，降低了向量数据库的强依赖风险

## 三、核心功能实现细节

### Q8: 多模态 VideoContext 是如何构建的？请详细说明流水线。

**考察层次**：中等 · 技术实现

`VideoContextService` 是整个流水线的核心，流程如下：

1. **音频切分**：FFmpeg 将视频中的音频按 60 秒切片，输出为 MP3 片段
2. **关键帧抽取**：同时使用 FFmpeg 的场景变化检测（scene detection）抽取关键帧，并以 30 秒为保底间隔采样，避免静态板书场景下无帧可抽
3. **并行处理**：
   - ASR 线程池：将音频片段发送到阿里云语音识别 API，获取带时间戳的转写文本
   - OCR 线程池：对关键帧进行 Tesseract OCR 识别，提取画面中的文字
4. **去重与合并**：相邻关键帧通过感知哈希（pHash）去重；将语音区间、OCR 文本、关键帧路径和时间戳合并为统一的 `VideoSegment`
5. **容错**：ASR 和 OCR 各自独立线程池，单路失败时保留另一路的有效信息，不阻断整体流程

```java
// VideoContextService 中的核心并行处理
CompletableFuture<List<SegmentResult>> asrFuture = 
    CompletableFuture.supplyAsync(() -> processAsr(audioPath), asrExecutor);
CompletableFuture<List<SegmentResult>> ocrFuture = 
    CompletableFuture.supplyAsync(() -> processOcr(framesDir), ocrExecutor);
CompletableFuture.allOf(asrFuture, ocrFuture).join();
```

### Q9: AgentLoop 的 Planner-Executor-Critic 架构是如何工作的？

**考察层次**：中等 · 技术实现

`AgentLoopService` 实现了受控的 Agent 编排：

```
用户目标 → Planner(拆解任务) → Executor(执行分析) → Critic(校验证据)
                                                      ↓
                                              未通过 → 补充检索 → 重执行
                                                      ↓
                                              通过 → 输出结果
```

**Planner**：调用 DeepSeek 生成结构化的执行计划，包含 `understoodGoal` 和 `tasks` 列表，每个任务必须可仅依靠 VideoContext 中的 ASR/OCR 证据完成。

**Executor**：按计划逐项执行，生成 `AnalysisResult`，包含标题、结论、证据（时间戳 + 来源 + 内容）、建议。所有结论必须绑定真实 `timestampMs`。

**Critic**：检查三个方面：
- 目标覆盖性：是否所有用户要求都被覆盖
- 结构完整性：结论是否有证据支撑
- 时间戳证据：证据是否在 VideoContext 中存在

**轮次控制**：最多执行两轮（`MAX_ROUNDS = 2`），既允许定向修正，也通过轮次上限控制延迟和 Token 成本。

### Q10: 长视频检索是如何实现的？为什么要分块？

**考察层次**：中等 · 技术实现

`LongVideoContextService` 实现了分块检索机制：

**分块原因**：一个 2 小时的视频可能包含数千个 `VideoSegment`，如果全部送入 Agent 的 Prompt，Token 消耗巨大且超出模型上下文窗口。因此需要筛选出与用户目标最相关的片段。

**实现方式**：
1. 每 5 分钟（`CHUNK_MS = 5 * 60 * 1000`）的片段聚合为一个 `VideoChunk`
2. 对每个 Chunk 调用 DeepSeek 生成摘要和关键词
3. 对摘要和关键词生成 Embedding，存入 Qdrant 向量库
4. 检索时，将用户目标转化为 Embedding，通过 Qdrant 语义召回 + 关键词匹配选取 TopK（`TOP_K = 3`）Chunk
5. 将选中的 Chunk 中的原始 `VideoSegment` 解包，构建新的 `VideoContext`

**降级策略**：Qdrant 或 Embedding 服务不可用时，退化为本地关键词匹配 + 已有向量排序，不阻断主分析链路。

### Q11: 断点恢复（Checkpoint）机制是如何设计的？

**考察层次**：中等 · 技术实现

`AgentCheckpointService` 和 `AgentCheckpointRepository` 实现了两级 Checkpoint 存储：

**存储架构**：
- **MySQL（恢复真源）**：通过 `AgentCheckpointRepository` 持久化完整的 Checkpoint 数据，包括 `VideoContext`、Chunks、Plan、Critic 状态、最终结果
- **Redis（热缓存）**：缓存活跃任务的 Checkpoint Key，加速状态查询

**断点恢复流程**：
1. 消费者启动时，先查询 Redis 中是否存在活跃任务状态
2. 如果存在已完成的 Checkpoint，直接返回结果（`terminalCheckpointHits` 指标）
3. 如果存在部分完成的 Checkpoint，从最近成功阶段恢复执行
4. 前端通过 SSE 实时接收任务阶段状态，断开后重连时自动恢复

**幂等控制**：通过 `AnalysisTaskKeys` 生成基于内容指纹 + 目标哈希的幂等 Key，确保重复消息不会重复执行。

### Q12: 分片上传的具体实现是怎样的？如何保证断点续传？

**考察层次**：基础 · 技术实现

`ChunkUploadService` 实现了分片上传：

1. **初始化**：前端调用 `/media/upload-init` 获取 `uploadId`，Redis 记录文件元信息（文件名、总分片数、用户 ID）
2. **分片上传**：前端按 5MB 分片，每片上传时携带 `uploadId` 和 `chunkIndex`，服务器将分片写入临时目录
3. **进度追踪**：Redis Set 记录已上传的分片索引，支持断点续传
4. **合并**：所有分片上传完成后，调用 `/media/complete-upload`，服务器按索引顺序合并分片，计算文件 MD5，上传到 MinIO
5. **断点续传**：前端 localStorage 存储 `uploadId`，重新进入页面时先查询已上传分片，只上传缺失部分

**并发控制**：前端控制 3 个并发上传（`UPLOAD_CONCURRENCY = 3`），通过 Redisson 分布锁防止合并阶段的并发冲突。

### Q13: SSE（Server-Sent Events）在项目中是如何使用的？

**考察层次**：基础 · 技术实现

`TaskEventService` 实现了 SSE 事件推送机制：

1. 前端创建 `EventSource` 连接到 `/analysis/analysis-events` 或 `/analysis/transcription-events`
2. 后端通过 `SseEmitter` 推送任务阶段事件，超时时间为 30 分钟
3. 事件类型：`TaskStage` 枚举，包括 `QUEUED`、`VIDEO_CONTEXT`、`AGENT_LOOP`、`CRITIC_PASSED`、`COMPLETED`、`FAILED` 等
4. 前端 SSE 断线后自动重连，重连时查询当前状态，避免重复消费

**与 WebSocket 的对比**：SSE 是单向推送（服务端 → 客户端），对于本项目"服务端阶段变化通知客户端"的场景完全够用，且实现比 WebSocket 更轻量，不需要额外的握手协议。

## 四、技术挑战与解决方案

### Q14: 在构建多模态上下文时，遇到过哪些技术挑战？如何解决？

**考察层次**：中等 · 问题解决

**挑战 1：ASR 和 OCR 处理速度不匹配**
- ASR 调用外部 API，耗时较长（数分钟）；OCR 处理单帧较快
- 解决方案：使用独立有界线程池并行执行，ASR 线程池和 OCR 线程池各自独立配置，互不阻塞

**挑战 2：静态板书场景下关键帧抽取困难**
- 场景变化检测在静态板书场景下无法触发，导致漏帧
- 解决方案：30 秒保底采样（`FALLBACK_FRAME_INTERVAL_MS = 30_000`），确保每 30 秒至少抽取一帧

**挑战 3：相邻帧重复导致 OCR 冗余**
- 视频中相邻帧内容几乎相同，OCR 重复识别浪费算力
- 解决方案：感知哈希（pHash）去重，计算相邻帧的哈希值，相似度超过阈值则跳过

**挑战 4：单路失败影响整体流程**
- ASR 或 OCR 任一路失败，整个分析流程中断
- 解决方案：`CompletableFuture.allOf` 结合超时控制，单路失败时记录日志，保留另一路有效信息继续执行

### Q15: 消费幂等和并发控制是如何实现的？遇到过重复消费问题吗？

**考察层次**：中等 · 技术实现

**幂等机制**：基于 `Redisson` 分布式锁 + Redis 状态标记

```java
String lockKey = AnalysisTaskKeys.lock(contentHash, goalDigest);
String activeKey = AnalysisTaskKeys.active(contentHash, goalDigest);
RLock lock = redissonClient.getLock(lockKey);

// 加锁，最多等待 5 秒
if (lock.tryLock(5, TimeUnit.SECONDS)) {
    try {
        // 检查是否已处理完成
        if (Boolean.TRUE.equals(redisTemplate.hasKey(completedKey))) {
            return; // 已处理，直接返回
        }
        // 标记为活跃
        redisTemplate.opsForValue().set(activeKey, "1", ACTIVE_TTL);
        // 执行业务逻辑
        aiService.analyze(mediaId, contentHash, userGoal);
        // 标记为完成
        redisTemplate.opsForValue().set(completedKey, "1", ACTIVE_TTL);
    } finally {
        lock.unlock();
    }
}
```

**并发控制**：通过 `AnalysisTaskKeys` 生成基于"内容指纹 + 分析目标"的锁 Key，相同视频 + 相同目标的任务互斥执行。

### Q16: 令牌桶限流是如何实现的？为什么需要用户级和全局两级？

**考察层次**：中等 · 系统设计

`AnalysisDispatchService` 中实现了两级限流：

```java
// 用户级：每分钟 5 次
RRateLimiter userLimiter = redissonClient.getRateLimiter("rate:user:" + userId);
userLimiter.trySetRate(RateType.PER_CLIENT, USER_REQUESTS_PER_MINUTE, 1, RateIntervalUnit.MINUTES);

// 全局：每分钟 30 次
RRateLimiter globalLimiter = redissonClient.getRateLimiter("rate:global");
globalLimiter.trySetRate(RateType.OVERALL, GLOBAL_REQUESTS_PER_MINUTE, 1, RateIntervalUnit.MINUTES);
```

**两级设计的原因**：
1. **用户级**：防止单个用户大量提交任务，占满系统资源，保障多用户公平性
2. **全局**：保护后端 AI 服务（DeepSeek API）不被打爆，控制整体成本

两个限流器同时检查，任一触发限流则拒绝请求，返回 `429 Too Many Requests`。

### Q17: 模型调用失败后的重试策略是什么？如何避免雪崩？

**考察层次**：中等 · 系统设计

`DeepSeekUtils` 中实现了指数退避重试（Exponential Backoff）：

```java
private void waitBeforeRetry(int attempt) {
    try {
        Thread.sleep(1_000L << attempt);  // 1s, 2s, 4s
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        throw new IllegalStateException("模型重试被中断", e);
    }
}
```

**重试参数**：
- 最大重试次数：`MAX_MODEL_ATTEMPTS = 3`
- 退避策略：1 秒 → 2 秒 → 4 秒（指数增长）
- 如果 JSON 解析失败，额外重试一次，并附加"请严格返回合法 JSON"提示

**雪崩防护**：
- 令牌桶限流：从源头控制请求速率
- 异步解耦：RocketMQ 削峰填谷，消费速率由线程池控制
- 有限重试：3 次重试后直接失败，不无限排队

### Q18: 如何看待 EvidenceVerificationService 中的文本匹配算法？为什么选择 bigram 而非精确匹配？

**考察层次**：中等 · 算法设计

Critic 校验证据时，需要判断 Executor 生成的证据内容是否与 VideoContext 中的原始内容匹配。由于 ASR 和 LLM 都可能引入轻微的表述差异，精确匹配会误杀有效证据。

**Bigram 匹配算法**：
1. 对证据文本和候选文本进行归一化（去标点、小写化）
2. 如果一方包含另一方，直接通过
3. 否则，计算双方 Bigram 集合的交集覆盖率，阈值 50%

```java
Set<String> evidenceBigrams = bigrams(normalizedEvidence);
Set<String> candidateBigrams = bigrams(normalizedCandidate);
long overlap = evidenceBigrams.stream().filter(candidateBigrams::contains).count();
return (double) overlap / evidenceBigrams.size() >= MIN_BIGRAM_COVERAGE;
```

这样既能容忍轻微的表述差异，又能防止模型凭空捏造证据。

## 五、性能优化

### Q19: 项目中有哪些性能优化的措施？

**考察层次**：中等 · 性能优化

1. **分片上传 + 并发上传**：5MB 分片，前端 3 并发上传，减少大文件上传的等待时间
2. **ASR/OCR 并行执行**：独立有界线程池，充分利用多核 CPU
3. **感知哈希去重**：减少冗余 OCR 调用，降低处理延迟
4. **分块检索**：5 分钟分块 + 摘要生成，避免全量 VideoContext 送入 LLM
5. **Redis 缓存**：Checkpoint 状态、上传进度、限流计数器等使用 Redis 热缓存
6. **RocketMQ 异步削峰**：视频分析任务通过消息队列异步消费，请求线程快速返回 `202 Accepted`
7. **SSE 推送**：替代轮询，减少前端无效请求

### Q20: 当视频时长很长（如 5 小时以上）时，系统会面临哪些挑战？如何应对？

**考察层次**：高级 · 架构设计

**挑战**：
1. VideoContext 过大，超出 LLM 上下文窗口
2. ASR 处理时间过长，超过 HTTP 超时限制
3. 中间某环节失败，从头重来成本极高

**应对方案**：
1. **分块检索**（`LongVideoContextService`）：每 5 分钟分块，只检索 TopK 相关块送入 LLM，避免全量上下文
2. **异步 + 消息队列**：整个分析流程在 RocketMQ 消费者中异步执行，不阻塞 HTTP 请求
3. **Checkpoint 断点恢复**：每个阶段完成后持久化状态，失败后从最近成功阶段恢复
4. **SSE 长连接**：30 分钟超时，前端断开后自动重连，查询当前进度

## 六、安全性设计

### Q21: 项目中做了哪些安全防护措施？

**考察层次**：中等 · 安全

1. **认证与授权**：
   - PBKDF2 密码哈希（210,000 次迭代，16 字节盐）
   - 随机 Token 会话管理（32 字节），Redis 存储，24 小时过期
   - 登录失败锁定：8 次失败后锁定 10 分钟
   - 输入长度限制：密码 128 字符、昵称 50 字符、分析目标 500 字符

2. **API 安全**：
   - `AuthInterceptor` 拦截器统一鉴权，提取用户 ID 注入请求属性
   - 媒体文件所有权校验：`requireOwnedMedia(id, userId)`
   - 管理员权限校验：`authService.requireAdmin(userId)`

3. **SSRF 防护**：
   - `YtDlpUtils` 中验证 URL 合法性，仅允许 HTTP/HTTPS 公网地址
   - 禁止访问本机地址、内网地址、回环地址

4. **敏感信息保护**：
   - `.env` 加入 `.gitignore`，不提交到版本控制
   - 配置文件中不硬编码密钥

### Q22: PBKDF2 的参数选择（210,000 次迭代）是怎么确定的？

**考察层次**：中等 · 安全实践

210,000 次迭代是参考了 OWASP 2023 年推荐的最小迭代次数。这是一个平衡点：
- 用户侧：注册/登录时的一次性延迟，200ms 以内可接受
- 攻击侧：暴力破解单次密码的成本足够高
- 选择 PBKDF2 而非 bcrypt/scrypt 的原因：Java 标准库原生支持，无需额外依赖

## 七、项目亮点与个人贡献

### Q23: 你认为项目中最有技术含量的设计是什么？

**考察层次**：中等 · 技术深度

个人认为最核心的设计是**受控 AgentLoop + 证据约束机制**。

传统的 LLM 应用是"一问一答"模式，模型可能输出幻觉内容。VidMind-AI 的 AgentLoop 通过 Critic 校验环节，让模型输出的每条结论都必须有 VideoContext 中的时间戳证据支撑，且证据必须通过 bigram 文本匹配校验。这形成了一个"生成-校验-修正"的闭环，大幅提升了分析结果的可靠性。

另一个亮点是**优雅降级设计**：Qdrant 不可用时降级到本地关键词排序、Embedding 服务不可用时退化到已有向量排序、单路 ASR/OCR 失败时保留另一路信息——每个关键依赖都有降级路径，不阻断主链路。

### Q24: 你在项目中具体负责了哪些部分？最大的贡献是什么？

**考察层次**：基础 · 个人贡献

独立完成了全栈开发与架构设计，包括：
- **后端**：Spring Boot 服务，涵盖鉴权、分片上传、任务编排、Agent 推理、向量检索、Checkpoint 持久化
- **前端**：Vue 3 工作台，包括 SSE 实时进度展示、Agent 交互面板、分片上传组件
- **中间件**：Docker Compose 编排（MySQL、Redis、MinIO、Qdrant、RocketMQ）

**最大贡献**：AgentLoop 的受控编排设计和多模态 VideoContext 流水线的容错实现，确保系统的可靠性和可观测性。

### Q25: 如果让你重新设计这个项目，你会做哪些改进？

**考察层次**：高级 · 架构演进

1. **Agent 引入更多工具**：当前 Agent 只能分析已有 VideoContext，可以扩展工具集，如搜索工具、数学计算工具等
2. **多视频对比分析**：支持用户选择多个视频，Agent 进行对比分析，这在课程对比、产品评测等场景很有价值
3. **实时流处理**：支持直播流实时分析，而非仅离线视频
4. **自适应分块**：当前分块大小固定为 5 分钟，可以基于内容复杂度自适应调整
5. **更细粒度的异步处理**：当前 ASR 是串行逐段处理，可以改为流式并行，进一步缩短处理时间

### Q27: 项目中遇到困难时是如何解决的？举个例子。

**考察层次**：基础 · 问题解决

**具体案例：Critic 循环不收敛的问题**

在早期版本中，AgentLoop 的 Critic 校验经常不通过，导致需要多轮重试仍然无法收敛，既消耗 Token 又增加延迟。

**分析过程**：
1. 首先通过 Telemetry 追踪发现，Critic 不通过的原因主要是"证据缺失"——Executor 生成的证据时间戳在 VideoContext 中找不到匹配
2. 进一步分析发现，是长视频检索阶段返回的 TopK 片段可能不包含 Executor 关心的内容
3. 解决方案：在 Critic 不通过时，提取缺失的时间范围，定向补充检索（`LongVideoContextService.selectRelevant`），而不是简单地重试 Executor

**结果**：Critic 不通过率从约 40% 降至 10% 以下，大部分任务在两轮内收敛。

## 十、技术栈深度追问

### Q30: MyBatis-Plus 在项目中的使用情况？为什么选择它？

**考察层次**：基础 · 技术栈

项目中 MyBatis-Plus 主要用于基础 CRUD 操作，如 `UserMapper`、`MediaFileMapper`、`FailedAnalysisTaskMapper` 等。选择理由：
- 单表操作无需手写 SQL，`BaseMapper` 提供常用方法
- 与 Spring Boot 3 集成良好
- 项目中大部分是简单的单表查询，复杂查询通过 `QueryWrapper` 即可满足

### Q31: Redisson 在项目中除了分布式锁，还用来做什么？

**考察层次**：中等 · 技术栈

1. **分布式锁**：`RedissonClient.getLock()` 用于消费幂等控制
2. **令牌桶限流**：`RedissonClient.getRateLimiter()` 实现用户级和全局限流
3. **（间接）Redis 操作**：项目中通过 `StringRedisTemplate` 操作 Redis，Redisson 核心能力是锁和限流器

### Q32: 项目中使用了 Jackson 的 ObjectMapper 来进行 JSON 序列化/反序列化，遇到过什么问题吗？

**考察层次**：中等 · 技术细节

**问题**：Agent 的 Plan、CriticResult 等嵌套 Record 类型的反序列化比较特殊，需要配置 Jackson 的 `activateDefaultTyping` 或使用 `TypeReference`。

**解决方案**：`AgentCheckpointService` 中统一使用 `objectMapper.readValue(json, new TypeReference<>() {})` 来处理泛型类型的反序列化。
